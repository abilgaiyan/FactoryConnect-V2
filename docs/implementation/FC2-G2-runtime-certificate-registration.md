# G2 exact runtime certificate registration

This increment closes the missing durable certificate/CA-pin prerequisite between signing-key enrollment and runtime authentication. It does **not** implement or enable an mTLS listener, authenticate a channel, check external CA revocation, acknowledge configuration, or publish an active roster. `EnrollRuntimeCertificateAsync` is a trusted server-side enrollment/rotation command, not an authentication endpoint. Existing key-only enrollment remains a signing-key prerequisite and never establishes X.509 trust.

The frozen G2 direction requires per-runtime X.509 client certificates, pinned trust anchor and exact certificate/generation binding in SQL. Deployment still needs an explicit issuing CA and operational revocation policy; no factory CA, public CA, machine certificate or production private key is inferred or provisioned here. Fixtures use generated disposable keys and certificates only.

A new certificate is registered atomically with a **new** signing-key generation through the same current installation-scoped `runtime.credential.manage` and independent two-custodian checks used by key enrollment. Rotation requires the exact current generation, invalidates its predecessor, and advances only credential generation. A certificate cannot be silently attached to or swapped within an existing generation. Assignment generations and all activation/acknowledgement facts remain unchanged.

All three private-key owners sign the exact same `FactoryConnect-V2:runtime-certificate-registration:v1` canonical envelope: the canonical credential authorization, exact public DER leaf and exact public DER trust anchor. The underlying authorization binds installation/runtime/human identity, operation ID, expected generation/security epoch, explicit credential interval, selected custodians, bounded ceremony interval, nonce and reason. Base64 encoding preserves exact bytes; the whole envelope must fit the existing 16 KiB immutable operation limit. Ordinary key-operation signatures cannot authorize this separate certificate domain, or vice versa. Mutable caller buffers are copied before asynchronous work.

The initial offline registration profile is deliberately narrow: canonical public DER only, RSA 3072–8192/exponent 65537, SHA-256-with-RSA certificate signatures, one directly issuing self-issued root, two certificate chain elements, critical CA constraints and CA signing/CRL-signing usage on the anchor, and a non-CA leaf with critical digital-signature-only usage and exactly the client-authentication EKU. The leaf public key must equal the new approved credential key. The leaf interval must fit the credential interval and both certificates must be currently valid. SAN/CN/display names never resolve runtime identity: the signed immutable identity and SQL generation do. Intermediates, multi-purpose leaves, floating/system trust and alternate chains are not accepted by this initial profile; they need a separate reviewed increment if deployment requires them.

Validation uses a custom trust store containing only the exact proposed anchor, no verification-flag overrides, disabled issuer downloads and a fixed SQL-generated evaluation time. **Revocation mode is NoCheck here solely for offline public-material registration. This routine must never be reused as a TLS authentication verdict.** A currently valid signed certificate may still be CA-revoked; successful registration intentionally makes no contrary claim. Runtime authentication remains closed until separate transport proof, exact certificate/anchor/current-generation lookup and fail-closed operational CA-revocation handling are implemented and tested. SQL credential/principal revocations remain authoritative for application eligibility, but do not replace external CA-status validation.

CA keys cannot reuse existing runtime, bootstrap or recovery custody material. Later runtime enrollment also rejects known runtime-CA keys; later recovery trust provisioning rejects both runtime and runtime-CA keys, preventing a reverse enrollment-order loophole. Reusing the same legitimate issuing CA for multiple runtime leaves is allowed. Private keys are never accepted/stored in the certificate registry, SQL, source, logs or receipts.

Migration 013 retains immutable exact leaf/anchor DER and SHA-256 pins, CA public-key digest, explicit certificate interval and exact credential/ceremony source operation. Foreign keys prevent attaching another generation's certificate or another operation's proof. Runtime key/identity/state, certificate binding, prior-generation invalidation, nonce/signatures, operation receipt, audit and epoch all commit in one transaction. Tests inject failure *after* certificate insertion to prove full rollback, not only pre-write rejection. Exact retries require fresh current human/custody authorization and return historical receipts without restoring old generation state.

The common operation-ID → exclusive installation-security gate order remains unchanged. Registration performs no network validation, raw-history scans or per-machine loop. Metadata-only sampling measures whole transaction roundtrips/duration; existing 100-machine assignment/activation/inventory regression checks remain required. CI ceilings are synthetic regression guards, not production throughput claims.

Acceptance includes pure X.509 profile/chain/key/interval/encoding checks and disposable real SQL using actual bootstrap, human enrollment and scoped grant commands. It covers signature-domain separation, private-key possession, changed certificate replay, concurrent exact retries, new-generation rotation, immutable exact pins, reverse custody key reuse, current permission denial and post-insert rollback. TLS handshake/private-key transport proof, CA revocation outages, authenticated read-vs-revocation races and HTTP runtime wiring remain the next boundary, not acceptance supplied by these tests.

API reference: [X509ChainPolicy](https://learn.microsoft.com/dotnet/api/system.security.cryptography.x509certificates.x509chainpolicy?view=net-10.0).
