# G3 durable runtime activation acknowledgement

`AcknowledgeActivationAsync` records a runtime's acknowledgement of one exact currently effective activation request. It requires the real mTLS channel from G2, current SQL certificate/key/credential/assignment authority, exact approved package revision/hash/review and current request generation. No human session, administrator bypass or human `runtime.acknowledge` permission exists. This is a trusted server-side command; no runtime HTTP route, production listener, active roster, connectivity indicator or production deployment is added.

The authenticated runtime attests that it applied the package. This is not independent physical proof that a CNC is working. The future host must parse the acknowledgement from the same owned channel used for authorization, never look up a channel based on a human-supplied identifier. SQL fixtures include a real length-bounded acknowledgement frame sent through TLS and decoded on that authenticated server channel. No general framing/HTTP protocol is exposed by the fixture.

## Exact facts and transaction order

The command binds operation/acknowledgement IDs, site/machine, activation ID/generation, package revision/SHA-256, exact approval, runtime identity, assignment ID/generation, credential generation, actual peer certificate digest and reason. All reusable generations use invariant decimal strings. Caller hash buffers are copied before asynchronous work. No runtime-supplied effective start, wall clock, verification flag or nearest timestamp selects authority.

CA/transport verification runs before SQL. Mutation order is operation-ID lock → installation security exclusive → sorted pinned policy shared locks → selected machine exclusive. Initial runtime authorization protects package retrieval and completed receipts; after all locks, SQL time and complete runtime authority are rechecked, including the five-second CA-verdict age bound. The common helper is also used by protected mTLS reads. No CA/network validation occurs under SQL gates, and no lock is upgraded or acquired in reverse order.

The exact approved canonical bytes are hashed again, selected machine scope/interval is verified, and current assignment/credential/certificate plus site/machine/line retirement, approval withdrawal, intent revocation and pinned timezone/schedule/break safety revocations are checked directly. A new acknowledgement must match the current activation-request head. It cannot acknowledge a superseded, ended, future, revoked or otherwise ineligible request. Explicit replacements are required after credential or assignment generation changes; existing acknowledgements never transfer.

Runtime acknowledgements compare these exact per-machine authority versions rather than a caller-supplied global security epoch. Unrelated security changes therefore do not manufacture cross-machine version conflicts. The security epoch still advances atomically for the committed acknowledgement/audit and is not treated as a universal publication revision.

The application start is the SQL evaluation instant captured after locks. A past request start does not backdate application; a future request cannot be acknowledged as already applied. Optional end remains the request's explicit half-open end. This interval does not extend certificate, credential, assignment or policy validity; future eligibility must recheck all authorities at its own protected cut.

## Durability, retries and historical facts

Migration 014 appends immutable acknowledgement rows, exact activation/package/approval/runtime/assignment/credential composite foreign keys, exact registered-certificate binding and runtime-actor operation provenance. One activation has at most one acknowledgement. A separate current acknowledgement pointer records the last acknowledged request; a pending activation pointer is not an acknowledged configuration. Acknowledgement, pointer, operation result, runtime audit and security epoch commit in one SQL transaction. Audit failure after row/head insertion rolls everything back.

An exact completed retry requires current same runtime/assignment/credential authority, then returns the original receipt without reapplying any effect. Changed content conflicts. Another operation/acknowledgement ID cannot duplicate an activation's logical effect. A newer acknowledgement cannot be overwritten by historical replay. Protected receipt retrieval requires the original runtime and current exact scope/generations. A stored receipt remains historical after intent supersession/revocation; it does not revive eligibility. Old credentials cannot retrieve acknowledgement authority through a rotated generation.

Both commit orders are explicit: acknowledgement-first may record a fact before subsequent revocation; revocation-first denies the queued acknowledgement. Revoked facts remain immutable for audit. A pending/failed replacement preserves the last acknowledgement fact, but neither that pointer nor a receipt is an active-roster verdict. Future retain-last behavior must reject expired/revoked/disabled or otherwise invalid prior facts. Machine enable/suspend producers and complete protected eligibility projection remain separate publication gates.

## Acceptance and performance

Disposable SQL fixtures use actual signed bootstrap, human enrollment/scoped grants, independent package review, controlled certificate enrollment, runtime assignment and real mTLS. They cover exact pins/generations/scope, current-runtime-only acknowledgement, concurrent exact retries and conflicting writers, no backdating, future/expired/superseded requests, caller-buffer mutation, immutable history, receipt privacy across rotation, explicit replacements and failure after acknowledgement/head insertion. SQL application-lock observations prove expiry while waiting and both acknowledgement/revocation commit orders. Policy/approval revocation source rows are explicit privileged upstream fixtures; their production mutation commands are not implemented by these tests.

A 100-machine/100-mapping approved package proves selected-machine acknowledgement uses only the three policy pins plus that machine, with a fixed full-path SQL roundtrip and duration ceiling. Existing 100-machine submission/activation, assignment, certificate, runtime read and inventory performance gates remain required. No historical activation traversal, raw observation scan, per-machine verification loop or dashboard timeout increase is introduced. Synthetic CI establishes correctness/regression budgets, not production capacity.
