# G2 increment 3 — Human session issuance authority

Baseline: main `2a222c4`, initial bootstrap squash-merged in PR #7. This increment adds a server-side session authority seam, not browser sign-in or a production identity-provider configuration.

`IHumanIdentityVerifier` is a trusted host dependency. Its output must follow validation of signature, exact issuer, intended audience, expiry, nonce/state and proof binding by the authentication adapter. The product registers no implementation, mock fallback, HTTP route or client-controlled verified-identity decoder. Synthetic verifiers are confined to SQL acceptance fixtures. OIDC provider integration remains a separate increment.

Issuance accepts only an existing, unrevoked human principal with exact UTF-8 issuer/subject bytes. It never enrolls a principal or grants permissions. The installation must be unsealed and its installation UUID must match. SQL UTC is sampled after gate acquisition; authentication must be no older than five minutes, not future-dated, and still valid. Session expiry is the earlier of proof expiry and one hour. These strict bounds intentionally require a new authentication ceremony after ambiguous completion, rather than replaying a secret.

A proof identifier must be issuer-scoped and unique to the verified authentication ceremony (not the subject or a reusable login identifier). SHA-256 of versioned canonical issuer/assertion-ID JSON is consumed once per installation, even across concurrent calls. The adapter is responsible for stable proof identity on retries. Sessions use 32 random bytes; callers present SHA-256 of the bearer to the existing authorization kernel. Only hashes are persisted; operation receipts/audit contain neither bearer nor original assertion. The hosting boundary must transport bearer material securely and keep it out of logs. This increment adds no such transport.

Lock order: private operation-ID lock → shared installation security gate → exclusive proof-consumption lock. No path acquires a proof lock before the security gate. Proof locks are local to issuance and precede no policy/machine locks. Principal/session/grant revocation uses the existing exclusive security gate. When revocation commits first, waiting issuance rechecks current authority and fails. When issuance commits first, later principal revocation denies the issued session on protected reads. A timestamp does not establish commit visibility.

Migration 005 adds immutable issuance history and unique proof/token constraints. Session, proof consumption, operation receipt and audit commit together. Audit failure rolls back consumption so a still-valid proof can be retried. A successful response lost in transit requires fresh authentication: no stored-result operation can recover a bearer secret. Failed issuance zeroes its local secret buffer.

Acceptance uses disposable SQL and synthetic verifier output. It covers sealed/wrong installation, exact identity and byte length, unknown/runtime identities, invalid/stale/expired/future proof, concurrent replay, bounded expiry, hashed storage, no implicit permissions, compatibility with protected reads, audit rollback, principal-revocation ordering and immutable history. It does not prove real OIDC validation, user-agent login/CSRF handling, controlled recovery, grant issuance, runtime enrollment or least-privilege SQL deployment.
