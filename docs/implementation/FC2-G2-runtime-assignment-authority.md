# G2 runtime assignment authority

`AssignRuntimeAsync`, `RevokeRuntimeAssignmentAsync` and `ReadRuntimeAssignmentOperationAsync` are trusted server-side commands requiring current `runtime.assign` for the exact authoritative site/machine. Security administration, package approval, credential management and runtime possession imply no assignment permission. Machine-scoped grants work without installation-wide access. No HTTP route, active roster, mTLS runtime login, configuration activation or acknowledgement is added.

Assignment requests name the installation through the authority instance, immutable assignment/site/machine/runtime IDs, current credential generation as a creation precondition, explicit half-open UTC interval, expected assignment generation, exact predecessor ID, expected security epoch, operation ID and reason. A new assignment starts at generation one with predecessor null/expected zero. Every replacement, including nonoverlapping or already-revoked heads, names the exact current head. Generations are lossless decimal strings in operation fingerprints/results. Normalized UTC instants make equivalent-offset retries identical.

The target must be a committed `R` runtime with an unrevoked principal and current, unrevoked signing-key generation whose retained public key matches the credential binding hash. A digest-only prerequisite fixture row does not satisfy this command. The credential must be valid at SQL evaluation time and the first intended use. An open-ended assignment does not extend credential validity. Ended intervals, retired site/machine, wrong ownership or missing authority fail closed. Line membership remains package-owned and is not invented here.

A successful replacement appends the assignment and actor/provenance record, revokes its predecessor immediately, and moves the single current pointer in the same transaction. This conservative initial profile has no automatic future handoff or grace period: a future-dated replacement invalidates the previous assignment at commit, so eligibility can have a visible gap until the new start. A past requested start does not certify historical runtime use. Revocation preserves the current pointer/generation as a tombstone; later reuse needs an explicit new assignment generation. Revoking an already invalidated predecessor cannot affect its replacement. A revocation receipt does not claim that an offline runtime has stopped.

Credential generation and machine assignment generation stay independent. Rotation leaves assignments unchanged; new activation must still pin the current credential generation, and existing acknowledgements cannot transfer. Assignment changes leave credential state, activation requests and acknowledgement history unchanged. A credential's validity/revocation is continuously relevant to subsequent eligibility, not established forever by assignment creation.

Lock order is operation ID → installation security gate exclusive → common machine resource exclusive. No policy locks are required because assignment alone makes no policy decision. This retains policy-before-machine ordering for other operations, never upgrades a lock and serializes across credential revocation, activation requests and future protected readers. SQL time, session, grant ancestry and expected epoch are rechecked after the machine gate. One machine request uses indexed current/exact keys; it does not traverse assignment history or scan raw evidence. The permission ancestry query is the existing bounded security check.

Exact retries reauthorize the actor, compare canonical operation bytes and return the original receipt without changing any state. Changed content conflicts. Protected receipt reads require the original actor and current exact-scoped assignment permission. Runtime assignment, supersession invalidation, operation result, provenance, audit and epoch commit atomically. Migration 012 adds immutable issuance provenance with same-site/machine predecessor, exact source-operation and actor-operation foreign keys; migration 010 remains unchanged.

Disposable SQL acceptance starts with real signed bootstrap, actual human enrollment/scoped grant issuance and controlled runtime credential commands. It covers missing/current credential and kind checks, permission separation, wrong site/installation/seal, explicit generations/predecessors, concurrent retries and competing replacements, UTC equivalence, open-ended/ended/empty intervals, audit rollback, credential rotation independence, immutable provenance, retired machines, exact revocation/tombstones, operation privacy and revoked access. A measured machine-lock wait crosses an SQL-clock session expiry and proves final authorization rejection without state changes. Existing inventory/100-machine submission/activation performance gates remain required; full-path assignment roundtrips have a fixed CI ceiling. This does not certify production throughput or complete runtime transport trust.
