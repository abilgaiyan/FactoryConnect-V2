# G2 runtime public credential authority

This increment supplies a trusted server-side command for controlled enrollment, immediate rotation and revocation of runtime signing keys. It does not implement mTLS, X.509 issuance/chain validation, runtime transport authentication, runtime acknowledgement, assignment writes or active roster publication. The key proof is an enrollment prerequisite, not evidence of a live authenticated connection. No HTTP host registration is added; production deployment remains unchanged.

`ChangeRuntimeCredentialAsync` requires current installation-scoped `runtime.credential.manage`, a live human session and exact actor issuer/subject binding. Security administration alone grants no bypass. Two independent, SQL-pinned bootstrap custodians sign every change, including revocation; neither may be the executing actor or the runtime identity. These offline public trust roots are reused for this controlled operation; private custody keys never enter SQL or the application. Revocation deliberately needs no runtime private key, so a lost/compromised key cannot prevent invalidation.

For enrollment/rotation, the new runtime private key must independently sign the same canonical bytes. RSA-PSS/SHA-256 signatures use the existing canonical DER SPKI profile (3072–8192 bits, exponent 65537). The request binds a separate runtime-operation domain, installation, operation ID, human and runtime exact identities, action, expected credential generation and security epoch, new public key, explicit credential interval, both custodians, bounded 15-minute ceremony interval, 32-byte nonce, pinned trust hash and reason. UTC instants normalize before signing; generation values use invariant decimal strings. A credential starts immediately and expires within 90 days of signing. This is the initial signing-key profile; it does not relax the frozen requirement for mTLS at future runtime boundaries.

Enrollment creates a separate `R` principal and immutable runtime identity with generation one, no human session or grants. Rotation checks the exact current generation, appends the next generation and public SPKI/hash, moves the current pointer and revokes the previous generation atomically. No overlap/grace period exists. An already revoked credential may be replaced by a newly approved rotation; principal revocation cannot be bypassed. Reusing previously enrolled key material, bootstrap/recovery custody keys or consumed nonces fails closed. Revocation preserves the current generation pointer and appends its invalidation; it does not claim to stop an offline runtime. Runtime-assignment generation and all existing activation intents remain unchanged. New generation use requires explicit assignment/activation operations under their own contracts.

All changes take the common operation-ID lock then installation security gate exclusively. This serializes with activation requests for every assigned machine, and avoids per-machine loops for global credential changes. SQL time/session/grant authorization is rechecked after crypto and database reads. Every exact retry requires current grant/session and valid current custody proofs; it compares original canonical bytes and returns only the original receipt, never reapplies enrollment or restores an older pointer. Ceremony expiry also applies to retries; a receipt is historical, not authority to renew a credential.

Migration 011 retains only public SPKI and signatures, nonce digest and operation provenance, with immutable proof tables. Credential identity/hash and state remain in migration 010. Historical prerequisite rows without retained public proof do not establish transport trust. The command's operation, new principal/key generation, old-generation revocation, ceremony, audit and security epoch commit in one SQL transaction; audit failure rolls everything back. Application SQL-role hardening, real runtime TLS identity verification and operator custody tooling remain required before production use.

Disposable SQL acceptance uses a real signed initial bootstrap and synthetic keys/sessions. It exercises exact identity and possession binding, threshold/duplicate/self approval denial, wrong installation, expiry, expected generations/epoch, changed operation replay, nonce/key reuse, concurrent exact retries, atomic audit rollback, immutable public keys, old receipt non-reapplication, rotation/revocation, no implicit assignment/activation/human session/grants, and an observed SQL application-lock race proving queued retries reject a committed permission revocation. Existing inventory and 100-machine activation performance checks still run; no V1 evidence scan, N+1 machine write loop, dashboard timeout increase or unprotected read is introduced. Synthetic CI proves correctness and regression budgets, not production capacity.
