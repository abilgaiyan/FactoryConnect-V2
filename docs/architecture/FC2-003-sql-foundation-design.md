# FC2-003 — Fresh SQL foundation: design proposal

**Status:** DRAFT — review only. No migration, database, deployment, or cutover authorized.  
**Baseline:** FactoryConnect-V2 main `a13e0b023343fefccabc38af564dce6f796c8394`  
**Test engine:** SQL Server 2022 Developer in a disposable Docker container (approved).  
**Database name:** `FactoryConnect_V2` (proposed, not yet approved).  
**Production engine, edition, instance, sizing and licensing:** UNDECIDED.

## 1. Boundaries and non-goals

FC2-003 creates a new V2 authority; it never imports legacy schema history, production evidence, checkpoints, machine mappings or configuration. No connection string or credentials from the existing Gajra production system may enter source, tests or CI. SQL tests must provision and dispose their own isolated database.

This document specifies design gates only. A separate implementation PR will add SQL migrations, SQL-backed roster, migration runner and disposable-SQL integration tests.

## 2. Schema proposal

| Schema | Owns in FC2-003 | Excluded until later |
| --- | --- | --- |
| `master` | Site, ProductionLine, Machine stable identity and relationships | Raw observations, counters, machine activity |
| `configuration` | ConfigurationRevision, MachineAssignment, SignalMapping, ShiftSchedule, BreakPolicy, Approval, ActivationAcknowledgement, ChangeAudit | Automated runtime recovery or historical corrections |
| `platform` | SchemaMigration ledger, database installation identity | Existing FactoryConnect migration ledger |
| `acquisition` | Reserved namespace, no tables in this slice | Evidence and ingestion checkpoints |
| `reporting` | Reserved namespace, no tables in this slice | Accumulators, shift summaries and OEE projections |

**Schema boundaries are proposed, not frozen.** Decide whether machine assignments, schedules and signal mappings should be revision-owned together or versioned independently before DDL.

## 3. Identity and relational integrity

- `SiteId`, `ProductionLineId`, `MachineId`: immutable GUID primary keys generated by V2 authority, never inferred from name, network address, adapter stream key or UI label.
- ProductionLine belongs to exactly one Site. Machine belongs to a Site; effective-dated line membership is represented as a configuration assignment, not a mutable machine identity.
- External machine aliases (controller serial, MTConnect device UUID, adapter stream key) are scoped, typed, effective-dated and unique within their declared authority scope. Ambiguous aliases block activation.
- Deactivation/retirement preserves identities and historical revision references. No cascading deletion of evidence-related identity.
- Concurrency uses explicit revision/row-version preconditions; invalid cross-site line assignment is rejected.

## 4. Configuration state and authorization

```text
Draft revision --[submit]--> Submitted --[approve]--> Approved
                                                    |
                                           [request activation]
                                                    v
                                             ActivationPending
                                                    |
                                       [runtime acknowledgement]
                                                    v
                                                Activated
```

- Revision content is immutable once submitted; a change creates a new revision.
- Approval records exact revision hash, approver, UTC timestamp, scope and decision; approver permissions are distinct from editor and activator.
- Activation is a separate durable request referencing exact revision, machine scope and effective period; **approval is not activation**.
- Runtime acknowledgement records per-machine applied revision, effective instant, runtime identity, operation ID, success/failure and observed time. Partial activation is visible, not represented as full success.
- Only successfully acknowledged, effective configuration can be returned as **active** by the roster.
- All transitions use authenticated actor identity, authorization, durable idempotency key and append-only audit. Authentication/permission implementation must be designed before exposing write endpoints.
- Revocation and recovery are separate operations. No direct SQL edits as an ordinary operational workflow.
- Time intervals use UTC instants plus explicitly identified site timezone and local shift semantics; reject overlap/ambiguity.

**Open policy:** initial administrator bootstrap, who can delegate access, approval segregation, and exact runtime-acknowledgement trust boundary require review before implementing write APIs.

## 5. Migration design

- Use a dedicated `platform.SchemaMigration` ledger with monotonically ordered immutable migration IDs, content SHA-256 and UTC applied timestamp.
- Migration runner connects only to an explicitly supplied V2 target, validates server/database identity and refuses known legacy database names; no implicit production defaults.
- Exclusive migration lock prevents concurrent installers; each migration and its ledger write commit atomically where SQL Server transactional DDL permits. Explicitly classify nontransactional operations.
- Existing migration with changed checksum fails closed. Reapply unchanged migrations as no-op. No automatic destructive downgrade.
- CI creates a uniquely named database per test job, runs fresh install, idempotent rerun, invalid checksum and failure rollback tests, then drops it in guaranteed cleanup.
- SQL Server 2022 Developer Docker is for disposable development/integration only. Secrets come from CI secret handling; no SA password in repository or logs.
- Record server product version/edition and migration identity in test evidence.

## 6. Dashboard roster contract

`GET /dashboard/config` must preserve the current dashboard JSON contract (`reportingBasePath`, positive `requestTimeoutMilliseconds`, `sources` and supported optional capability profiles).

- The roster comes from a consistent SQL read of **acknowledged and currently effective** machine assignments and signal configuration.
- A machine with draft/approved-but-not-activated configuration is not presented as live.
- Return empty `sources` only when SQL authority is healthy and the active roster is genuinely empty.
- SQL unavailable, incomplete schema or configuration integrity conflict returns explicit 503 Problem Details; never silently substitute fixtures.
- No implicit Vite mock fallback in real-backend integration mode; a separate integration slice will prove end-to-end routing.
- Authentication/authorization and sensitive connection details must not leak through the roster.

**Open:** decide how roster represents disabled machines, partial activation, and capability profiles, using existing React decoder fixtures before freezing the response.

## 7. Integration and acceptance matrix

| Test | Required proof |
| --- | --- |
| Fresh install | All approved schemas and constraints created from empty SQL Server 2022 Developer database |
| Idempotent install | Second run no-ops without schema drift |
| Migration corruption | Changed checksum rejected before any application |
| Failure recovery | Transactional migration failure leaves no partial applied state |
| Identity | Stable GUID, cross-site/line constraints and duplicate external alias rejection |
| Revision lifecycle | Immutable submitted revision; edit, approve and activate separated |
| Runtime acknowledgement | Partial/failure activation not advertised as fully active |
| Roster | Active configuration mapped to dashboard contract; empty healthy versus 503 unavailable |
| Concurrency | Duplicate operation replay, expected revision conflict and concurrent activation |
| Isolation | Test database cleaned; no production/legacy connection or migration path |
| CI | Dashboard typecheck/tests/build + .NET build + disposable-SQL integration tests |
